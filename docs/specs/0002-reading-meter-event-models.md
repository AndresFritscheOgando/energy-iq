# P1-01 Reading and meter event models

**Status**: Accepted

## Summary

Define validated Python records for cumulative meter readings and meter events. These records give later ordering and interval work stable inputs. They do not persist data or calculate consumption.

## Context

Phase 0 accepts bare timestamp and Decimal pairs. Phase 1 needs meter identity, reading provenance, status, and explicit discontinuity events before it can reject duplicates or compute intervals safely. The data contract leaves reading scale and date only input rules open.

## Requirements

1. **AC-1**: A reading has UUID identity and meter identity, a UTC instant, finite nonnegative cumulative kWh, source, status, creation time, and optional local date, note, and source reference. Invalid types or values fail at construction.
2. **AC-2**: Reading values have at most six meaningful fractional digits and cannot exceed `999999999999.999999` kWh. Validation never rounds, converts through float, or changes the caller's Decimal context.
3. **AC-3**: A meter event has UUID identity and meter identity, an event kind, UTC effective and creation instants, optional note, and optional paired approval actor and instant. Invalid types, enum values, or incomplete approval metadata fail at construction.
4. **AC-4**: The models are immutable. Timestamp validation accepts aware zero offset datetimes and rejects date only, naive, and nonzero offset values. A local date is provenance only and never supplies an invented UTC instant.
5. **AC-5**: Tests cover valid models, invalid boundaries, immutability, and ambient Decimal context preservation. Applicable pytest and Ruff checks pass, and the contract and progress records reflect observed results.

## Options considered

1. Standard library dataclasses with enums and explicit validation. They fit the current dependency free domain and make invalid states hard to construct. The cost is hand written guards that later API schemas must map explicitly.
2. Pydantic models now. They would ease later JSON validation, but add a dependency and mix the domain with Phase 2 transport concerns.
3. Bare typed tuples or dictionaries. They are small, but cannot enforce the reading and event invariants at construction.

## Decision

Use frozen, slotted dataclasses and string enums in `energyiq.readings`. Keep the existing pure Phase 0 helpers available. Use `Decimal` with a future PostgreSQL `NUMERIC(18,6)` compatible bound. Reject unsupported values rather than quantizing them. Accept exact UTC instants only. The caller must supply a UTC instant even when it also stores the original local date.

## Rationale

The domain needs reliable inputs before interval logic exists. Explicit guards keep it independent of FastAPI and a database. Six fractional places allow finer digital readings while bounding input and preserving exact subtraction under the existing 28 digit calculation policy. A timestamp cannot be inferred from a date without property timezone and a time of day, so date only entry waits for an explicit policy.

## Feature design

| Record | Required fields | Optional fields | Relationship |
|---|---|---|---|
| `Reading` | `id: UUID`, `meter_id: UUID`, `recorded_at: datetime`, `cumulative_kwh: Decimal`, `source: ReadingSource`, `status: ReadingStatus`, `created_at: datetime` | `original_local_date: date`, `note: str`, `source_ref: str` | Many readings belong to one meter |
| `MeterEvent` | `id: UUID`, `meter_id: UUID`, `event_type: MeterEventType`, `effective_at: datetime`, `created_at: datetime` | `note: str`, `approved_by: UUID`, `approved_at: datetime` | Many events belong to one meter |

`ReadingSource` is `manual` or `import`. `ReadingStatus` is `valid`, `flagged`, or `voided`. `MeterEventType` is `installed`, `reset`, `replaced`, `rollover`, or `calibration`. Approval fields must be both present or both absent. These fields record state, but this ticket does not define status transitions or event approval operations.

The interface is dataclass construction. It raises `TypeError` for unsupported field types and `ValueError` for invalid values. There is no HTTP endpoint, storage, authentication, configuration, external provider, or migration in P1-01. Phase 2 must enforce owner scope before constructing or returning these records from stored data.

| Produced value | Source |
|---|---|
| Reading and event identifiers | Explicit UUID constructor arguments, generated by a future use case |
| UTC reading, event, creation, and approval instants | Explicit datetime constructor arguments |
| Cumulative kWh | Explicit Decimal argument, validated without modification |
| Local date and provenance text | Optional explicit constructor arguments |
| Event kind, source, and status | Explicit enum constructor arguments |

Reading construction does not reject duplicates or decreases against another reading. Event construction does not mark a reset or replacement as a normal interval. P1-02 and P1-03 apply collection rules using these records. No real account data belongs in fixtures.

Critical test scenarios: a normal manual reading and approved replacement event satisfy AC-1 through AC-4; nonfinite, over scale, over bound, and wrong runtime values satisfy AC-1 and AC-2; date only and non UTC timestamps satisfy AC-3 and AC-4; the full suite and static checks satisfy AC-5.

## Build plan

1. Add validated reading enums and a reading dataclass with focused tests, satisfies AC-1, AC-2, AC-4.
2. Add the event enum and dataclass with approval metadata tests, satisfies AC-3, AC-4.
3. Run full checks, review domain boundaries, and update affected documentation, satisfies AC-5.

## Consequences

Later Phase 1 code can depend on validated, typed records. API adapters will need to parse external data and turn domain errors into transport errors. The six digit scale is a storage compatibility choice and may need a documented migration if real meter specifications require more precision later. Date only entry remains unavailable until its deterministic ordering rule is designed.

## Follow-up

P1-02 must define duplicate timestamp handling. P1-03 must define how approved events divide intervals. Phase 2 must map these domain records to owner scoped storage and API schemas.
