# Review, features (P3-01 AC-18 case-sensitivity fix, re-review), 2026-11-05

**Reviewed by**: Opus 5.5 (author on a different model)
**Scope**: 4 files, uncommitted (`README.md`, `frontend/next.config.ts`, `frontend/scripts/check-edge-proxy.mjs`, `frontend/tests/next-config.test.ts`)
**Verdict**: Approve with nits

## Summary
The change closes the blocker from `2026-11-05-features-p3-01.md`. It sets `experimental.caseSensitiveRoutes: true`, so the `/api/:path*` rewrite stops matching `/API/...`. After that, every path the rewrite forwards to FastAPI is also a path the `proxy.ts` matcher catches. I checked the whole bypass class live, not just letter case: 55 raw-socket probes against a production `next start` of the repo build, plus the same probes in a scratch `next dev` with the flag on and with it off as a control. Nothing reached the backend with a spoofed `X-Forwarded-For` while the flag was on. With the flag off, only the letter-case variants leaked, so the new probes do catch the bug. What remains is defense in depth and documentation. The safety now depends on two Next.js matchers agreeing, and one of them is an `experimental` flag. Neither the ADR nor the spec records that invariant, and the only test that exercises real behavior is a script you run by hand.

## Minor
### 🟡 The invariant "every FastAPI rewrite is covered by the `proxy.ts` matcher" is pinned by config, not by structure, and is not in ADR-008 or the spec, `frontend/next.config.ts:81` (with `frontend/src/proxy.ts:31`)
**Problem**: AC-18 now holds only while three conditions stay true. First, `caseSensitiveRoutes` stays `true`. Second, Next keeps honoring that flag; it is under `experimental`, and the startup banner says "use with caution". Third, every rewrite to FastAPI sits under a source the `/api/:path*` matcher also covers. The unit test pins the first condition. Only the manual `scripts/check-edge-proxy.mjs` covers the second. Nothing covers the third: a future `beforeFiles` or `fallback` rewrite to FastAPI outside `/api` (for example an uploads path) would bypass `proxy.ts` with no failing test. The previous review also asked for a line in the spec and ADR-008 saying the matcher and the rewrite must agree, and that line was not added. Neither file mentions `caseSensitiveRoutes`. The fix is recorded only in `PROGRESS.md`.
**Why it matters**: Today this is not exploitable. I verified the rewrite set is a subset of the matcher set across case, encoding, slash, dot segment, method, and header variants (see Test coverage). The risk is a quiet regression on a Next upgrade or a later config edit, and AGENTS.md asks for significant security invariants to be recorded in the ADR.
**Suggested fix**: Add one sentence to ADR-008's AC-18 bullet and to spec AC-18: `caseSensitiveRoutes` must stay `true`, and every rewrite that reaches FastAPI must fall inside the `proxy.ts` matcher. Optionally make the invariant structural, so it no longer depends on two matchers agreeing: drop the matcher, or use a negative matcher that excludes only `_next/static`, `_next/image`, and `favicon.ico`. Deleting `X-Forwarded-For` on page requests is harmless. Optionally also add a cheap test that every source returned by `config.rewrites()` starts with `/api/`, which catches the third condition. Do not try to test this with `unstable_getResponseFromNextConfig`. Its `buildCustomRoute` hardcodes `sensitive: false` (`next/dist/lib/build-custom-route.js:17`), so it would report `/API` as rewritten even with the fix in place. That is another reason the live script is the real tripwire.

### 🟡 The live tripwire is not run by any automated gate, `frontend/scripts/check-edge-proxy.mjs:88`
**Problem**: The new probes have teeth. The author's PROGRESS row and my control run both show `6.6.6.6` leaking with the flag off. But the script is manual: no `package.json` script runs it, there is no CI workflow, and `pnpm test` covers only the config value. If a Next bump renames the flag or makes it a no-op, `pnpm test` stays green, because Next warns about unknown `experimental` keys but does not fail.
**Why it matters**: ADR-008 names this script as "the tripwire if a later Next.js release changes this behavior". That only works if someone remembers to run it after an upgrade.
**Suggested fix**: Add a `check:edge-proxy` script to `package.json`. List it next to the other checks in the README, and in the spec's or roadmap's upgrade checklist for any `next` version bump. Running it in CI is the better option once CI exists.

## Nits
- ⚪ `frontend/scripts/check-edge-proxy.mjs:90`, the case probes assert only that `6.6.6.6` is absent. Asserting the response status is 404 states the intent ("not rewritten" rather than "rewritten but stripped") and catches a crashed server directly. Adding one `POST` (login is a POST) would mirror the real attack. Rewrite matching ignores the method, so this is clarity only.
- ⚪ `README.md:91`, "The `/api` rewrite adds no client address" is slightly off. The script's own `true` check shows Next filling the socket address (`::ffff:127.0.0.1`) when the browser sent none and the request passed through `proxy.ts`. ADR-008 states this correctly. Align the README with the ADR, and consider one clause noting that routes are case sensitive, so `/API/...` returns 404.
- ⚪ `frontend/next.config.ts:77`, the comment is accurate. It could also say that the flag affects only `rewrites`, `redirects`, and `headers` (custom routes). App Router page matching is already case sensitive, so readers do not wonder about side effects. I confirmed `/Login` returns 404 and `/login` returns 307 on the built server.

## Strengths
- The fix is minimal, applies to `next dev` and `next start` (both build custom routes through `filesystem.js` with the runtime flag), and is the option the previous review recommended. Its side effects are limited to custom routes: the `/:path*` security header rule still matches everything, and there are no redirects.
- The author confirmed the probes fail with the setting reverted, so the new check really catches the bug.

## Test coverage
- `next-config.test.ts`: pins `caseSensitiveRoutes === true`. It is a config pin, not a behavior test. That is acceptable, given that Next's own config testing helper ignores the flag (see the first minor finding).
- `check-edge-proxy.mjs` (rerun by me with `SKIP_BUILD=1` against the author's existing build, which has `caseSensitive: true` in its routes manifest): all 7 checks PASS. The case probes received `[]` in both modes.
- My own raw-socket matrix (55 requests, `ENERGYIQ_EDGE_PROXY=false`, `X-Forwarded-For: 6.6.6.6` on each, echo server in place of FastAPI). I ran it against the repo's production `next start` and against a scratch `next dev --webpack` with the flag on, then with the flag off as a control:
  - Letter case (`/API`, `/Api`, `/aPI`, bare `/API`): 404 with the fix, nothing forwarded. With the flag off, these were the only leaks (`xff: "6.6.6.6"`).
  - Trailing slash, `//api`, `/api//v1`, backslashes, and absolute-form request targets: 308 or 400 before routing, nothing forwarded.
  - Percent encoding (`/%61pi`, `/%41PI`, `/%2561pi`, `/ap%69`, `/api%2F...`, `/api%00`, `/api%20`, `/api;x`, `/x/..%2Fapi`): 404 even with the flag off. Rewrites match the raw pathname, while `proxy.ts` matches the raw or the decoded pathname (`resolve-routes.js:343-350`), so the matcher catches a superset of what the rewrite forwards.
  - Encoded segments inside `/api/` (`/api/v1%2Fauth%2Fme`, `/api/v1/auth/%6De`), dot segments (`/./api`, `/x/../api`, `/api/%2e%2e/api`), and query tricks: forwarded, with `proxy.ts` run and `xff: null`.
  - `/_next/data/x/api/...json`: 404 (App Router only).
  - Methods: `POST`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`, and `PATCH` on `/api` were all stripped. On `/API` all returned 404.
  - Header tricks: `x-middleware-subrequest` with `proxy`, `src/proxy`, `middleware`, and `src/middleware` chains (the CVE-2025-29927 class); a forged `x-middleware-override-headers` / `x-middleware-request-x-forwarded-for`; `x-invoke-path` and `x-matched-path`; a duplicate `X-Forwarded-For`; and `rsc`. All arrived with `xff: null`. The backend reads only `X-Forwarded-For`, never `Forwarded` or `X-Real-IP`.
- In scratch dev, the 500s on unmatched paths came from a cross-drive webpack resolution limit of the scratch setup, not from the app. The repo's production server returned clean 404s.
- I did not rerun `pnpm lint`, `typecheck`, or `test`. I relied on the author's PROGRESS row for those (155 passed). I stopped every process I started and removed the scratch app and its `node_modules` junction; the junction target is intact. A pre-existing `scratchpad\caseapp` directory from an earlier session was left untouched.
- The earlier minors (`X-Forwarded-Proto` passthrough, stale rate limit docstring and PROGRESS row, page `no-store`) and nits remain open as recorded in the previous review. They are out of scope for this diff and are not raised again here.
