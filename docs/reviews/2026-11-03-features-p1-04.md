## Summary
Adds `readings/normalization.py` (per interval kWh/day, exact window coverage, typed gaps), extracts `exact_kwh_context()` from `calculate_consumption`, and exports the new names. The arithmetic (integer microseconds, `Fraction`, one half even rounding, digit tuple Decimal construction) is correct, the gap algorithm tiles the window in every edge case I traced, and the extraction preserves behavior (303 tests pass, re-run by me). Findings are all Minor or Nit: a ratio-rounding contract trap, a confusing failure for out of range hand built intervals, thin record cross checks, and some doc hygiene.

## Minor
### 🟡 `coverage_ratio` can read 1.0000 (or 0.0000) while gaps or coverage exist, `normalization.py:360`
**Problem**: The ratio is rounded to 4 places, so covered 99,999,999/100,000,000 of a window yields `Decimal("1.0000")` with a nonempty `gaps` tuple, and 1 s of 20,000 s yields `0.0000` with `average_kwh_per_day` set (the test at `test_reading_normalization.py:300` even asserts `0.0000` for covered 1 s).
**Why it matters**: A later API/UI consumer that tests `coverage_ratio == 1` to mean "fully measured" would present a window with a hole as complete, which is the exact "gap mistaken for zero/complete" failure the spec exists to prevent.
**Suggested fix**: Document in the summary docstring and spec 0005 Consequences that completeness must be judged from `uncovered == timedelta(0)` / `gaps == ()`, never from the rounded ratio. Optionally add a test pinning the 1.0000-with-a-gap case.

### 🟡 Out of range kWh on a hand built interval fails with a misleading error, `normalization.py:56`
**Problem**: `ConsumptionInterval` only requires finite and nonnegative kWh. `normalize_intervals([iv(kwh=Decimal("1E+999999"))])` (I ran it) raises `ValueError: Exceeds the limit (4300 digits) for integer string conversion` from `str(abs(scaled))`, after building a ~10^1,000,000 integer via `Fraction(Decimal)`. Intervals from `compute_intervals` are bounded by the `Reading` maximum, so this is not reachable from the real pipeline.
**Why it matters**: Public pure function with untrusted-input posture (AGENTS.md); the failure is an unrelated message, and the work is unbounded in the exponent. Low likelihood.
**Suggested fix**: Build the digit tuple without `str()` of a huge int (or reject rates above a stated bound with a clear `ValueError`), or note the precondition that intervals come from `compute_intervals`.

### 🟡 Records accept values that contradict the fields they summarize, `normalization.py:97-160, 163-218`
**Problem**: `NormalizedInterval` does not check `kwh_per_day` against the interval; `ConsumptionWindowSummary` does not check `measured_kwh == sum(...)`, `covered == sum(measured durations)`, `uncovered == sum(gap durations)`, that measured intervals are inside the window, or that gap bounds lie inside the window (the spec data model table says "both inside the window"). The spec chose not to recheck tiling, which is defensible, but the cheap sum/containment rules are listed in the table.
**Why it matters**: The records are public and constructible; a later caller or deserializer can build an internally inconsistent summary that validates.
**Suggested fix**: Add the cheap consistency checks (sums, containment, gap in window), or state in the spec that records only validate field shape and the functions are the sole trusted producers.

## Strengths
- Single `_round_once` helper: `Fraction.__round__` is half even and exact, and building the Decimal from a digit tuple avoids any context rounding. I verified tie cases (0.0000005, 0.0000015, 0.0000025) and the 1 microsecond case reasoning by hand; all match the tests.
- Window algorithm is O(n), uses half open bounds correctly: touching intervals are skipped (`end <= window_start`, `start >= window_end`), windows entirely before or after the data collapse to one whole window gap, a single interval chain works, and a window inside one valid interval gives one `partial_interval`. Invalid intervals crossing a bound stay `invalid_interval` and are trimmed.
- `exact_kwh_context()` extraction is a pure move: identical `Context` arguments, fresh instance per call, `calculate_consumption` unchanged and still wrapped in `localcontext`. The summed `measured_kwh` is also shielded from the caller's context (tested with `prec=2`).
- Chain validation is shared by both functions, materializes once, and gives indexed messages; hole vs overlap distinguished.
- Strong test suite: real `compute_intervals` chain in the mixed gap test, tiling helper, recursive no float check, record rejection tests, bound touching, context independence.
