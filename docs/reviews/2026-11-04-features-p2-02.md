## Minor
### 🟡 Engine does not hide SQL parameters, `backend/src/energyiq/platform/db.py:63`
**Problem**: `create_engine` is called without `hide_parameters=True`. The generic 500 path in `middleware.py:88` uses `_error_log.exception`, which logs the full traceback. For any database error that is not an `OperationalError` or pool timeout (for example `IntegrityError`, `DataError`, `ProgrammingError`), SQLAlchemy puts the statement and the bound parameters into the exception text.
**Why it matters**: Once child 0002 inserts users, those parameters include email and `password_hash`. AC-6 only covers the 503 path, which is handled well (class name only), but the other path leaks into logs.
**Suggested fix**: Pass `hide_parameters=True` in `build_engine` (and the migrator engine if you want symmetry). Add a test that an unmapped `IntegrityError` raised in a route does not put the parameters in the log record.

### 🟡 Tests trust `ENERGYIQ_*` from the shell and can touch a non test database, `backend/tests/conftest.py:92` and `:101`
**Problem**: `DB_SETTINGS = AppSettings(env="test")` is read at import, and `ENERGYIQ_DATABASE_URL` or `ENERGYIQ_MIGRATION_DATABASE_URL` set in the developer shell override the test defaults. The session fixture then runs `alembic upgrade head` with the migrator DSN, and `test_readiness.py` runs `CREATE DATABASE` and `DROP DATABASE ... WITH (FORCE)` through the same engine.
**Why it matters**: A developer who exports their dev (or worse, a shared) migration DSN and runs pytest migrates that database from the test suite. Inserts are rolled back, but the schema change and the scratch database operations are real.
**Suggested fix**: In `migrator_engine`, refuse to continue (fail, not skip) unless the database name ends in `_test`, and say so in the message.

### 🟡 Tests hardcode revision `0001`, `backend/tests/db/test_readiness.py:89` and `:103`, `backend/tests/db/test_schema.py:119`
**Problem**: The expected revision is the literal `"0001"`. Child 0002 adds revision 0002, so `test_ready_at_head`, the lifecycle test and `test_database_is_at_the_script_head` will fail for a reason unrelated to the behavior under test.
**Why it matters**: Guaranteed churn at the next build step, and a pointless red build.
**Suggested fix**: Compare against `script_head()` everywhere. Keep one place that asserts the first revision id if needed.

### 🟡 Readiness engine can open up to 11 connections for an unauthenticated route, `backend/src/energyiq/main.py:82`
**Problem**: `build_engine(settings, pool_size=1, ...)` leaves `max_overflow` at the SQLAlchemy default of 10. `/health/ready` is public.
**Why it matters**: A burst of anonymous requests can hold up to 11 extra connections, which counts against PostgreSQL `max_connections` and can starve the app pool. The intent of `pool_size=1` is clearly to bound this.
**Suggested fix**: Add a `max_overflow` parameter to `build_engine` and use a small bound (for example 1 or 2) for readiness. Note that a tight bound makes concurrent probes return 503 under load, so pick it knowingly and document it.

### 🟡 The migrator inherits the app statement timeout and a forgotten `ENERGYIQ_ENV` yields a known secret key, `backend/alembic/env.py:47`, `backend/src/energyiq/platform/settings.py:50`
**Problem**: (a) `env.py` and the test fixtures use `connect_args(settings.db_statement_timeout_ms)` for the migrator, so every migration statement is limited to 5 s by default. Revision 0001 is tiny, but a later `CREATE INDEX` or backfill on real data will be cancelled. (b) `env` defaults to `dev`, and `dev` fills in the published `LOCAL_SECRET_KEY` and local DSNs. A prod deploy that forgets `ENERGYIQ_ENV=prod` boots with a publicly known secret key instead of failing. (c) `env.py` builds full `Settings()`, so a prod migration job also needs `ENERGYIQ_SECRET_KEY`, which it does not use.
**Why it matters**: (a) future migration failures that look random; (b) the secret fallback is the one place where "fails closed" does not hold; (c) minor deployment friction.
**Suggested fix**: (a) give the migrator its own, larger or disabled timeout. (b) Record this as a known limitation in the umbrella, and consider failing when the key equals `LOCAL_SECRET_KEY` and the bind address or any non loopback DSN is used. (c) Read only the migration URL in `env.py`, or document the requirement.

## Strengths
- Migration and ORM agree, and the suite proves it three ways: `alembic check`, exact `pg_constraint` and `pg_indexes` name sets, and normalized partial index definitions.
- Privilege design is tight and tested: column level UPDATE grants per revision, no DELETE or DDL, a test that the app role owns nothing and cannot create in `public`, and a clean `REVOKE` in `downgrade()`.
- The 503 path logs only the request id and exception class, and the tests assert that the DSN, SQL, parameters and host never appear in the body or the log.
- Test isolation is correct: outer transaction plus `create_savepoint`, an explicit two test proof that rows do not leak, and a subprocess test for the skip versus `ENERGYIQ_REQUIRE_DB=1` behavior.
- Secrets are `SecretStr` with a `missing` error for prod, and `repr`, `str` and `model_dump` are tested not to render them.
- One violating insert per rule (36 cases) plus accepted boundary cases, so both sides of each constraint are covered.
