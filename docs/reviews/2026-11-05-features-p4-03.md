## Summary
The change implements P4-03 build plan steps 1 and 2: the parse child now extracts text one page at a time, normalizes it (`n1`), fails closed with `pdf_text_too_large` rather than truncating, and the parent re-validates every page (order, count, digest, quality code, size, NFKC, no control/format characters) before the worker stores `pages` in `extraction_runs.output`. The design is sound and fail-closed, the output never reaches the API, and owner deletion clears it. The headline issue is that the child's normalization is not actually idempotent/NFKC-stable, so the parent can reject a valid child result. Other findings are a mismatch between the 1 MiB output cap and the 1 MiB text ceiling, missing parent bounds on `page_count`, and baseline metrics that are a little rosier than what they measure. No blockers or majors.

## Minor
### 🟡 Child normalization can produce non-NFKC text, so the parent rejects a valid result, `backend/src/energyiq/worker/pdf_child.py:57-71` / `backend/src/energyiq/documents/pdf_text.py:109`
**Problem**: `normalize` runs NFKC first and then drops Cc/Cf/Co/Cn characters. When a dropped character sat between a base letter and a combining mark, the remaining text is no longer NFKC. I reproduced this in the repo venv: `"e‌́"` gives `"é"`, and so do Hangul jamo separated by U+200B, `a + soft hyphen (U+00AD) + U+0308`, and `n + NUL + U+0303`. The parent's `unicodedata.normalize("NFKC", text) != text` check then makes `parse_pages` return `None`, and the whole document fails as `pdf_parse_failed`. That also breaks the docstring claim, and the property implied by the test at `test_pdf_native_text.py:52`, that normalization is idempotent: `normalize("é") != "é"`.
**Why it matters**: It fails closed, so nothing is corrupted, but a legitimate PDF (soft hyphens and zero-width characters are common in generated PDFs) fails with an opaque generic code. The child's output is also not exactly what the parent accepts, which was a stated design goal.
**Suggested fix**: Filter characters first and run NFKC last, or run NFKC again after filtering and collapsing. Add the four inputs above as parametrized cases that assert both idempotence and `parse_pages(...) is not None` on `page_record(...)`, so the test checks that child and parent agree with each other and not just against hand-picked strings.

### 🟡 The 1 MiB output cap cannot carry the 1 MiB text ceiling, `backend/src/energyiq/worker/sandbox.py:29` / `backend/src/energyiq/platform/settings.py:114`
**Problem**: `pdf_max_text_bytes` allows up to 1 MiB (spec 0002 hard ceiling), but `MAX_OUTPUT_BYTES` is a fixed 1 MiB that must also hold the JSON keys, a 64-char digest per page, and escapes (`\n`, `"`, and `\` each take 2 bytes). With the ceiling configured, a document whose text is legitimately under the limit overflows the cap and is reported as `pdf_parse_resource` instead of succeeding or returning `pdf_text_too_large`. At the 256 KiB default, worst-case doubling is 512 KiB, so the defaults are safe.
**Why it matters**: The reason code is wrong at a documented, valid configuration, and nothing in settings validation or tests ties the two limits together.
**Suggested fix**: Derive the output cap from the text limit (for example `2 * max_text_bytes + per-page overhead * max_pages`), or validate that the text limit leaves headroom. Add a test at the ceiling.

### 🟡 The parent does not bound the child's `page_count`, `backend/src/energyiq/worker/sandbox.py:95-106`
**Problem**: The parent rechecks pages against `count` but never checks `1 <= count <= limits.max_pages`. A child result of `{"ok": true, "page_count": 0, "pages": []}` is accepted as success with zero pages, and the updated `test_the_child_inherits_no_secrets` now relies on that. A tampered child could also report more pages than the limit, as long as the output fits the cap. The rest of the module treats the child as untrusted, and this is the one gap.
**Why it matters**: The real child never emits this, so the impact is low. Still, a zero-page "succeeded" run reaching `needs_review` contradicts the child's own `pdf_malformed` rule, and the parent's defence is meant to hold without relying on the child.
**Suggested fix**: Reject `count < 1 or count > limits.max_pages` in `_parse` (pass `max_pages` in as `max_text_bytes` already is) and have the env leak test emit one valid empty page.

### 🟡 Child failure codes are passed through unvalidated (pre-existing, widened here), `backend/src/energyiq/worker/sandbox.py:107-109`
**Problem**: Any string the child returns in `code` becomes `error_code` and is exposed as `reason_code` through `GET /documents/{id}`. This change adds `pdf_text_too_large` to the set. Spec 0002 requires a "safe reason code", but the parent never checks the code against an allowlist.
**Why it matters**: If the parser is compromised or misbehaves, it controls a string that is stored and shown to the user. The impact is low because the code is only shown as text, but it is the same untrusted-child principle this change otherwise enforces well.
**Suggested fix**: Accept only a known set (`pdf_encrypted`, `pdf_malformed`, `pdf_too_many_pages`, `pdf_text_too_large`, `pdf_parse_resource`) and map anything else to `pdf_parse_failed`.

### 🟡 Baseline metrics overstate what they measure, `backend/evals/native_text.py:54-61, 140-147, 185-213`
**Problem**: (a) `expected` is documented as "strings ... the page really shows", but the `noisy_ocr_layer` case expects `BILL_FIELDS`, which are not on that page (`35O kWh` is). Its 0/5 therefore measures the corpus design, not the extractor, yet it lowers the headline "field coverage 42/47". (b) "field coverage" is substring presence, not field extraction. (c) "False text" is only counted on image-only pages, so misread or garbage text on native pages (the false-text risk AC-3 is really about) is never measured. (d) `forbidden` is documented as "must never appear", but the hidden-instruction case is expected to appear and the report says it is extracted by design.
**Why it matters**: This report is the evidence that will choose a fallback (AC-4). Misnamed metrics can mislead that decision, even though PROGRESS discloses the noisy misses.
**Suggested fix**: For the noisy case, either expect the strings the page actually shows and report a separate "correct-value" metric, or exclude it from coverage. Rename `forbidden` to something like `hidden_strings` and report it as "hidden text extracted". Rename "field coverage" to "known-string recall".

### 🟡 AC-3 is marked built without the resource numbers it requires, `docs/specs/0012-phase-four-bill-intelligence/0003-pdf-native-text.md:29`
**Problem**: AC-3 requires the report to cover "resource use". The published report says memory and CPU were not measured. Even on Linux, `_peak_rss_kib` reports only peak RSS (a cumulative maximum over all children) and no CPU time. Build plan step 2 is still marked "Built 2026-11-05".
**Why it matters**: The project rule is to mark work complete only with evidence. PROGRESS records the gap honestly, but the spec line does not.
**Suggested fix**: Mark step 2 as partially built, with resource use not measured until a container run, or add `ru_utime + ru_stime` from `RUSAGE_CHILDREN` and run the baseline in the worker container.

### 🟡 No integration test stores real page text through PostgreSQL or confirms it stays out of the API, `backend/tests/db/test_documents.py:424-430`
**Problem**: The only worker-to-database test uses blank `make_pdf` pages, so no test round-trips actual text (accents, newlines, quotes) through JSONB, and no test asserts that a document with `has_text` pages returns no text in `GET /documents/{id}`. The protection is currently structural: `DocumentOut` and `RunOut` simply have no field for it.
**Why it matters**: Page text is private bill data. A later schema change that adds `output` to `RunOut` would leak it, and no test would catch it.
**Suggested fix**: Add a database test that uploads `build_pdf([["Período ... RD$ 1,250.00"]])`, runs the worker, asserts the stored `pages[0].normalized_text` and digest, and asserts that the serialized response body contains neither the text nor `pages`.

### 🟡 The published report is in a gitignored directory, `docs/evals/native-text-baseline.md`
**Problem**: `/docs` is gitignored. The spec and PROGRESS link to `docs/evals/native-text-baseline.md` (and `.json`) as published evidence, but a plain `git add` will not include them.
**Why it matters**: The AC-3 evidence would be missing from the commit, leaving dangling links.
**Suggested fix**: `git add -f docs/evals/` when committing, or add `!/docs/evals/` to `.gitignore`.

## Nits
- ⚪ `backend/src/energyiq/worker/pdf_child.py:66`: `Zl` and `Zp` (U+2028/U+2029) are dropped, which joins words (`"Total 350"` becomes `"Total350"`). Mapping them to `\n` would keep the token boundary.
- ⚪ `backend/src/energyiq/worker/pdf_child.py:25`: `NORMALIZATION_VERSION` is duplicated and unused in the child. The runner records `pdf_text`'s constant, so a change to the child's algorithm would not change the recorded version. Have the child emit its version and the parent check it, or add a test that asserts the two constants are equal.
- ⚪ `backend/src/energyiq/documents/pdf_text.py:46-62`: Span offsets are Python code points. Document this for P4-05, because a browser highlights in UTF-16 units and astral characters would shift the highlight.
- ⚪ `backend/tests/test_native_text_corpus.py:13-17`: `run_case` repeats each case 3 times for timing, which means 36 child spawns in the unit suite. The test also never asserts `found == expected` for the native cases, so a regression in extraction would pass.
- ⚪ `backend/src/energyiq/worker/pdf_child.py:111`: Exceptions that pypdf raises from `extract_text` outside the caught set (IndexError, AttributeError, ZeroDivisionError, NotImplementedError) end in a traceback and exit code 1, which `_crash_code` maps to `pdf_parse_failed`. That is safe, but a comment saying so would help, as would a test with a crafted page that crashes `extract_text`.
- ⚪ `backend/src/energyiq/documents/pdf_text.py:120-122`: `native_text` is true if any page has text, so a scan with a native header or footer counts as native. The spec does not allow a threshold yet; consider adding that layout to the corpus so the baseline shows it.

## Strengths
- The parent re-validates the child's output thoroughly: page order and count, digest, quality code, size, NFKC form, and no control characters. The parametrized tampered-result test covers each rejection branch.
- The design fails closed and never truncates (`pdf_text_too_large`). The size is measured the same way, normalized UTF-8 bytes across all pages, in both the child and the parent.
- The privacy design holds: `output` is never serialized, owner deletion and the worker's tombstone check both null it, the engine uses `hide_parameters=True` so page text cannot reach error logs, and the child's `ensure_ascii=False` with surrogates dropped avoids both output inflation and JSONB `\u0000` failures.
- `Span` and `quote()` give an exact round trip with page and range guards, and test the contract directly.
- The synthetic corpus contains no real data and covers the required layout kinds, including hidden render-mode-3 instruction text, which is documented as inert data.

## Test coverage
New logic is well covered: normalization cases, per-page extraction, accents, rotation, span round trips and guards, scans and partial scans, encrypted, malformed, too many pages, text over the limit (single page and cumulative), instruction text, and a full set of tampered child results. Targeted run in this review (Windows): `test_pdf_native_text.py`, `test_native_text_corpus.py`, `test_document_worker_units.py`: 67 passed, 2 skipped (Linux-only rlimit tests). Gaps:
- No test checks that child and parent agree on adversarial Unicode (the NFKC bug above).
- No test covers the output cap against the configured text ceiling.
- No test rejects a zero or over-limit `page_count`.
- No database or API test uses real text.
- The corpus test asserts nothing about recall on the native cases.
- CPU and memory limits during real extraction remain unverified outside Linux.
